Job Apply Agent

Source · Node.js, OpenAI JSON agents, LaTeX, local browser autofill

A local assistant for job applications. I built it to take the repetitive work out of searching, tailoring, and filling, without handing over the parts that need judgment.

The stack

A Node server that runs locally with a small dashboard on top of it. A queue store owns application state. OpenAI workers handle search planning, match reasoning, resume choices, and answer drafting. Resumes compile through LaTeX and the generated PDF gets validated before anything uses it. Form filling goes through a local browser bridge.

Where the model is allowed to decide

The model never gets the final say on anything with a consequence. Queue transitions, resume PDF validation, and submit confirmation are all deterministic code. What the model does is propose: plan the searches, score the fit, choose which bullets to use, draft the answers.

Every one of those comes back as JSON validated against a schema rather than prose I have to parse. That is the difference between a bad response failing loudly at the boundary and a bad response becoming a malformed resume three steps later.

Fit scoring runs early and cheap, before tailoring or drafting, so obvious mismatches never reach the expensive calls.

Filling a form is not submitting it

The autofill path and the LLM path are kept separate on purpose, and filling never submits. Submission waits for explicit confirmation. Keeping the two apart means a bug in the drafting code cannot turn into an application I did not intend to send, which is not a failure mode you get to apologize your way out of.

What stays out of git

Generated artifacts, the queue store, local profile data, the real resume, and API keys are all gitignored, with example files committed in their place. The repo is public and the project is inherently full of personal data, so the split had to be decided at the start rather than cleaned up later.
