InfoBolt

infoboltai.com · Python, FastAPI, Docker, Supabase, OpenAI, React

A support inbox for Shopify brands that drafts replies against real order data. It is the project I spend most of my time on, and I built and run all of it: the backend, the admin panel, the embeddable widget, the servers, and the deploy pipeline.

The stack

The backend is Python 3.12 on FastAPI and uvicorn. It holds the chat endpoints, a separate agent per channel, OAuth for Shopify, Gmail, and Meta, and a WebSocket hub for live inbox updates. The admin panel is React 19 with Vite and TanStack Query, built into the API image at build time and served from /admin. A second nginx container serves the embeddable widget and proxies everything else through.

Supabase is the Postgres layer, Stripe handles billing, and Langfuse traces model calls. It all runs as Docker Compose behind host nginx with Let's Encrypt, across three VPS hosts: production, staging, and a self-hosted Firecrawl instance for scraping merchant sites during onboarding.

Skills as files, not prompt rows

Reply instructions live in markdown files with YAML frontmatter, one per conversation type. The system prompt carries a single line about each, and the model calls invoke_skill to pull the full text when it decides it needs it.

The obvious alternative was prompt strings in Postgres with an editor in the admin panel. I went with files because it makes per-client customization a diff. A brand that wants returns handled its own way gets a handle_return_request.md in a client directory that shadows the base file at load time, and that change gets reviewed, deployed, and reverted like any other code. The cost is that clients cannot edit their own prompts. So far that has been the right trade, because the ones who ask for changes want them tested, not typed into a textarea.

The deploy pipeline

A push to main runs ruff, eslint, both test suites, and a Docker build check, then rebuilds staging over SSH. Production is a manual dispatch, so nothing reaches customers because I merged something on a Friday.

Schema migrations run between docker compose build and up -d. After the build, so the new image already has the driver and the SQL files. Before the swap, so no running code ever observes a half-migrated database. Under set -e a failed migration aborts with the old containers still serving.

Every migration gets a sha256 checksum once applied, which means editing one that already ran fails the next deploy rather than being skipped in silence. Anything containing DROP TABLE, DROP COLUMN, TRUNCATE, or DELETE FROM is logged and left pending for me to run by hand. The database credential sits in each host's env file instead of GitHub Secrets, since the deploy is already running on the box over SSH. No Postgres password needs to enter GitHub, and each host can structurally only reach its own project.

Two infrastructure constraints I design around

Cross-host port allowlists belong in the DOCKER-USER iptables chain, not ufw. Docker publishes container ports by writing its own rules, and that traffic is forwarded, so it traverses FORWARD and DOCKER-USER and never reaches the INPUT chain ufw filters. Mine is installed as a systemd unit ordered after docker.service so it holds across reboots, and the deploy re-asserts it every time.

The widget has to load on merchant sites as a classic script rather than a module, because module-type loads hit CORS cross-origin. So the embed snippet carries the client id and token as data attributes, and the boot script reads them off its own tag and injects the stylesheet itself. For the same category of reason, everything browser-facing lives on one origin, which keeps admin OAuth popup messages same-origin.
