Market Bubble Live

Source · Node.js, SQLite, server-sent events, Docker, Chrome extension

A host streams to Twitch and Kick at the same time while other people talk about the same stream on X, and the audience ends up split across four chat rooms that cannot see each other. Market Bubble Live merges them into one feed, with a combined viewer count and a chip on each message showing where it came from.

Three surfaces run off one server: the viewer page with the player and chat, a chat-only page meant to be dropped into OBS as a browser source, and a password-protected admin page for editing which sources are live.

Four connectors, four different shapes

No two platforms hand you chat the same way, so each connector is shaped by whatever that platform actually allows.

Twitch connects read-only over IRC through a WebSocket from the browser. Stream status and viewer count come from Helix server-side, so the client ID and secret never reach the page.

Kick pushes rather than being polled. Messages arrive at a webhook endpoint, get their signature verified, are normalized into the shared message shape, then go out to whoever is connected.

X has no usable path, so it gets a Chrome extension. A content script watches the live chat DOM on the page and posts what it sees back to the server. It is not elegant and it is the only thing that works today. The docs treat it as a bridge and note where an official API would slot in whenever that becomes possible.

Everything converges on one normalized message shape and fans out to browsers over server-sent events.

Surviving a reconnect

Chat events go into a SQLite log on a persistent Docker volume rather than being held in memory. A browser that drops its connection comes back with a cursor and replays what it missed, and that keeps working across a server restart. For this volume of messages it saves running a separate database service for what is essentially an append-only list.

Twitch's native emotes render straight from the IRC tags. Third-party emotes from 7TV, BetterTTV, and FrankerFaceZ are fetched and cached server-side per channel, since the alternative is every viewer's browser hitting three emote APIs on page load.

Admin auth

The admin password is stored as a pbkdf2 hash in a gitignored file on the data volume, and that file outranks the environment variable seed. So the password can be changed from the panel and survive a redeploy without anyone editing env config on the server. When no password is configured at all, admin is open, which is convenient locally and needs setting before the thing is exposed.
