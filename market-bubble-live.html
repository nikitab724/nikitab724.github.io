Market Bubble Live

Source · Node.js, SQLite, server-sent events, Docker, Chrome extension

One livestream runs on Twitch and Kick at the same time while people discuss it on X, which leaves the audience split across chat rooms that cannot see each other. I built the server that merges them, plus the viewer page, an OBS overlay surface, and an admin panel.

The stack

Node with no framework, just the built-in http server. The browser side is vanilla ES modules. SQLite holds the event log, server-sent events deliver it, and Docker Compose brings the whole thing up including its data volume. There is also a Chrome extension, which takes some explaining.

Server-sent events instead of WebSockets

Chat here only flows one direction, server to browser. SSE has reconnect and a last-event cursor built into the protocol, so I did not write reconnect logic or heartbeats, and it passes through nginx without upgrade handling. A WebSocket would have been more machinery for a duplex channel I have no use for. If the product ever needs browsers to send, I will regret this, and that is a reasonable thing to be wrong about later.

SQLite instead of an in-memory buffer

The event log goes to SQLite on a persistent Docker volume. A browser that drops its connection comes back with a cursor and replays what it missed, and that survives a server restart, which an in-memory ring buffer would not. For this message volume it costs one file and no second service.

Four connectors, four shapes

Twitch is read-only IRC over a WebSocket from the browser, with stream status and viewer counts fetched server-side through Helix so the client secret never reaches the page.

Kick pushes rather than being polled. A webhook endpoint verifies the signature, normalizes the payload into the shared message shape, and broadcasts it.

X has no usable API for this, so it gets a Chrome content script that watches the live chat DOM and posts back to the server. I do not like it. It is the only thing that works today, so the docs call it a bridge and note where an official API would slot in.

Native site chat posts straight to the server. Everything converges on one normalized shape before the fan-out, which is what keeps the renderer from knowing or caring where a message came from.

Caching and auth

Twitch native emotes render straight from the IRC tags. Third-party emotes from 7TV, BetterTTV, and FrankerFaceZ get fetched and cached server-side per channel, because the alternative is every viewer's browser hitting three external APIs on page load.

The admin password is a pbkdf2 hash in a gitignored file on the data volume, and that file outranks the environment variable seed. So the password can be changed from the panel and survive a redeploy without anyone SSHing in to edit env config, which is the kind of thing that otherwise never gets rotated.
